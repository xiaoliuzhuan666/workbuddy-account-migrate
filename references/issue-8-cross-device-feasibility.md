# Issue #8 可行性评估：跨设备项目迁移

> 评估日期：2026-10-06 ｜ 评估基线：v1.6.3 ｜ Issue 作者：@ZongbingHou（2 天前，无评论）
>
> 原文：可否实现跨设备的项目迁移。比如在电脑A的项目A，账号A，然后迁移至电脑B，项目A，账号B。主要场景是家用电脑和办公电脑两个账号，两地交替进行项目工作。

## 0. 结论（TL;DR）

**可以做，建议开发。** 核心迁移机制（跨库插入、`user_id` 改写、正文/工具结果复制、冲突分级、备份回滚）在 v1.6 单对话迁移里已全部实战验证，本期约 70% 是"组装"而非"发明"。

真正的新难点**只有一个：跨设备路径重映射**（电脑 A 的项目路径 ≠ 电脑 B）。本次实测确认路径存在于 **4 个位置**：

1. `sessions.cwd`（DB 字段）
2. `workspaces.path`（工作区登记）
3. `projects/{slug}/` 目录名（slug 由 cwd 推导）
4. **正文 jsonl 每条消息顶层的 `cwd` 字段**（本次实测发现，此前文档未记录）

建议拆两期：

| 期 | 内容 | 覆盖场景 | 预估 |
|:--|:--|:--|:--|
| 一期 | `migrate_project.py export / import`（项目维度打包迁移，copy 语义） | Issue 场景完整覆盖 | 2~3 天开发 + 两台真机验证 |
| 二期 | 双向增量同步（"两地交替"的长期形态） | 同步引擎 | 复杂度高一个量级，建议一期上线看反馈再决定 |

## 1. 需求拆解：四个技术诉求 vs 现有能力

| 诉求 | 现有能力 | 缺口 |
|:--|:--|:--|
| ① 跨设备（数据物理搬运） | ❌ 现有脚本只能读本机数据目录，无导出/打包能力 | **全新** |
| ② 跨账号（A → B） | ✅ `user_id` 改写已在 migrate.py / migrate_session.py 验证 | 无 |
| ③ 项目维度批量（既非单会话也非整账号） | ❌ 现在只有 `--session-id` 单会话和整账号两极 | 中等 |
| ④ 目标机路径与源机不同 | ❌ 完全没有 | **全新，最难** |

**场景判断**："两地交替" ≠ 一次性迁移，用户终态想要的是"项目跟着人走"（双向同步）。但一期先做单向搬运是成立的——因为导入用 **会话 id 稳定 + 同 id 覆盖** 语义（已有），反复导入同一项目天然近似增量同步，能撑很久。

## 2. "一个项目"在磁盘上的数据构成（迁移清单）

| 数据 | 位置 | 归属维度 | 一期策略 |
|:--|:--|:--|:--|
| sessions 表行 | `workbuddy.db`，按 `cwd` 筛选 | 账号 + 机器 | ✅ 导出/导入，`user_id` 与 `cwd` 改写 |
| session_usage 行 | 同库 | 同上 | ✅ 随会话走 |
| workspaces 登记 | 同库 `workspaces` 表 | 全局 | ✅ 导入侧按新路径登记 |
| 对话正文 | `projects/{slug}/{sid}.jsonl` + `.meta.json` + `.file-rollback.ndjson` | slug 由 cwd 推导 | ✅ 打包，slug 按目标机路径重推导 |
| 工具结果 | `projects/{slug}/{sid}/tool-results/`（目录） | 同上 | ✅ 整目录打包（Windows 目录坑已修过） |
| 任务 | `todos/{sid}.json`、`tasks/{sid}/` | 按 session，无账号隔离 | ✅ 顺手打包 |
| **工作区记忆 / 项目技能** | `{项目}/.workbuddy/memory/`、`{项目}/.workbuddy/skills/` | **在项目目录里** | ✅ 可选打包（若用户 git 同步项目则自动带走，需确认 .gitignore 未排除） |
| 账号级 memory / connectors | `~/.workbuddy/memory/{uid}_*`、`connectors/{uid}/` | 账号，不属于项目 | ❌ **明确不迁**（边界，回复 issue 时说明） |
| edge-sync 云通道映射 | `edge-sync-mapping*.db` | 账号 + 机器 | ❌ copy 语义下源机不动、目标机新增，无需处理 |

**本次实测支撑**：

- 本机 `sessions` 表 **43 列**，而 SKILL.md 记录的另一版本是 **30 列** → 两台机器版本漂移是现实威胁，"按列名对齐插入"（已实现）是刚需而非优化
- jsonl 每条消息顶层带 `cwd` 字段（实测确认）→ 路径重映射必须处理正文文件，不只是 DB
- 抽样的最新会话**没有** `.meta.json` → 打包逻辑需把 meta / rollback 文件当"可选"处理

## 4. 一期方案：`migrate_project.py export / import`

### export（源机）

1. **选项目**：读 `workspaces` 表 + `sessions` 按 `cwd` GROUP BY，列出项目（路径 / 会话数 / 最后活动 / 体积），输序号选择
2. **收集**：该项目全部会话及其 usage、正文、tool-results、todos/tasks，可选 `{项目}/.workbuddy/`
3. **manifest.json**：源 cwd、源 uid、客户端版本、每个会话的 id / 标题 / last_activity_at / jsonl 行数——导入侧靠它做冲突判断与增量二期的基础
4. **打包** `tar.gz`（标准库 tarfile，保持零依赖）

传输由人完成（AirDrop / U 盘 / scp / 网盘），不做网络功能。

### import（目标机）

1. 探测登录态 uid（account-snapshot，已有逻辑）
2. 指定项目在本机的**新路径**（参数或询问；必须真实存在，强校验——这是防"迁移成功却打不开"的关键）
3. **重映射**：`sessions.cwd`、`workspaces.path` 改写为新路径；slug 用新路径重推导（**不得沿用源 slug**）；jsonl 顶层 `cwd` 字段值逐行改写（仿 `_rewrite_session_id()`：只动结构化字段值，不碰消息文本里出现的路径字符串）
4. 按列名对齐插入；同 id = 硬冲突 → 覆盖（沿用源 id 原则），同标题不同 id = 软冲突 → 询问
5. 备份 → checkpoint → 验证 → 提示重启

### 二期（观察后决定）：双向增量同步

- export 支持 `--since`（基于 manifest 里的上次导出时间）只打包增量
- 冲突策略从"单会话询问"升级为"项目级策略"（新者胜 + 变更报告）
- 本质是带冲突解决的同步引擎，建议一期上线后按真实反馈决定是否投入

## 5. 关键风险与对策

| # | 风险 | 等级 | 对策 |
|:--|:--|:--:|:--|
| 1 | slug 沿用源机目录名而 cwd 改成了新路径 → 客户端按 `projects/<slug>/<sid>.jsonl` 找不到，"迁移成功却打不开"（仓库里同款坑已发生过） | 🔴 | import 侧一律用**新路径**重推导；注意与已有"优先沿用目标侧已存在目录"逻辑的先后关系 |
| 2 | 版本漂移：两台机器客户端版本不同（43 列 vs 30 列实测存在） | 🔴 | 列名对齐（已有）；"新版导出 → 旧版导入"方向文档声明限制 |
| 3 | jsonl 内嵌 cwd 字段（实测确认存在） | 🟡 | 字段级改写；需实测客户端对改写后的接受度 |
| 4 | "继续对话"时 cwd 指向目标机不存在路径的行为未验证 | 🟡 | import 强制校验新路径真实存在 |
| 5 | 反复导入产生双份对话 | 🟡 | id 稳定 + 硬冲突覆盖（已有语义天然防重） |
| 6 | 消息文本 / file-rollback 里的旧绝对路径 | 🟢 | 不改——历史记录属用户可见内容（沿用既有原则） |
| 7 | 客户端未关闭导致写入被覆盖 | 🟢 | 已有检测 |
| 8 | 工作区记忆被 .gitignore 排除导致 git 同步漏带 | 🟢 | export 可选打包 `{项目}/.workbuddy/` |
| 9 | 账号级记忆 / 连接器被误期待 | 🟢 | 回复 issue 明确边界：不在项目迁移范围 |

## 6. 零开发替代方案（回复 issue 时应先给）

1. **同一账号两台设备登录**：EdgeSync 本来就跨设备同步（v1.6.3 修的正是"换设备看不到"的反向 bug，反证同账号换设备看得到历史）。若账号政策允许，该场景零成本覆盖。issue 用户用两个账号大概率是公司/账号政策约束——所以才需要工具方案。
2. **项目目录走 git**：对话之外的项目资产（工作区记忆、项目技能）本就在 `{项目}/.workbuddy/`，随代码同步自动走。缺的只是**会话历史**——这正是本工具要补的。
3. **今天的临时手动方案**（PoC 级，有数据风险）：把源机 `~/.workbuddy` 整目录拷到目标机（**先备份目标机数据，此操作会覆盖目标库**），再跑 `migrate.py --source <A的uid> --target <B登录uid>` 合并。缺点：全账号粒度、路径无重映射（会话 cwd 仍是源机路径）、目标机原有数据有丢失风险。只建议当验证手段，不当方案宣传。

## 7. 测试策略

- **fixture 扩展**：`prepare_fixture.py` 造"两台机器"（两个假 home、不同 uid、不同 cwd 路径风格、不同列数的 schema）
- **新用例**：路径重映射正确性、slug 重推导、jsonl cwd 字段改写范围（只动顶层字段）、同 id 重复导入防重、manifest 完整性
- **真机矩阵**：macOS ⇄ Windows 优先（路径风格差异是重映射的极端用例：`C:\` 盘符小写化 vs `/Users/`）；国内版⇄国内版先行，国内⇄国际作为 stretch goal
